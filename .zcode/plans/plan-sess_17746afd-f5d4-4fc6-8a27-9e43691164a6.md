Route expert/unified/instruct chat through `ChatEngine` so MMI relevance reranking (the documented fix for "grammatical but irrelevant" output) runs in every mode, not just specialist.

## Root cause
`SodaAgent._chat_reply` (agent.py:246-250) calls `lm.chat()` directly for expert/unified/instruct modes — a single-sample generation with no reranking. Only specialist mode goes through `ChatEngine.reply()`, which samples 12 candidates and keeps the most context-relevant one (MMI). Since `expert.pt` exists, the default mode is `expert`, so relevance filtering is skipped by default — exactly the reported symptom.

## Changes

**1. `sodachat/engine.py` — let `ChatEngine` wrap a pre-built LM**
Add an `lm` parameter to `ChatEngine.__init__`. When given, skip `_load_backend` and use the passed instance directly (set `self.backend` to a sensible name from the LM). The standalone frontends (cli/discord/google) keep using `backend=`/`model_path=` unchanged (`lm` defaults to `None`). `reply()` is untouched — it already calls `self._lm.generate_line` and `self._lm.logprob`, so any LM satisfying that protocol works.

**2. `sodachat/expert.py` — add the chat protocol to `ExpertLM`**
Add two methods (mirroring `MiniChatLM`'s, model.py:234/250), prepending the `CHAT` tag and routing to the `TEXT` expert:
- `generate_line(self, prompt, temperature=0.8)` → `self._gen(f"{CHAT}\n" + prompt, TEXT, 48, temperature).strip()`
- `logprob(self, context, continuation)` → encode `f"{CHAT}\n" + context` + `" " + continuation + "\n"`, one forward pass with `task=TEXT`, take `lm_head` logits (`forward` returns `(lm_logits, action_logits)`), gather per-token logprobs over the continuation, return the mean.

This reconstructs the exact format the expert model trained on (`<|chat|>\nA:…\nB:`) from the tag-agnostic `build_prompt`/`null_prompt` output.

**3. `sodachat/unified.py` — add the same protocol to `UnifiedLM`**
Add `generate_line` and `logprob` analogously, prepending `CHAT` and using the plain `MiniGPT` forward (UnifiedLM's model is a stock MiniGPT, no task routing). `logprob` mirrors `MiniChatLM.logprob` exactly but with the `CHAT`-tagged context. This also covers `instruct` mode, which loads `unified-instruct.pt` as a `UnifiedLM`.

**4. `sodachat/agent.py` — route all chat through `ChatEngine`**
In `_chat_reply`, when an active LM exists, wrap it in a cached `ChatEngine(lm=…)` and call `.reply()` (MMI runs). Specialist mode unchanged. Add an `self._engines: dict` cache keyed by checkpoint path (so the `_recent` dedup deque persists per mode), populated via a small `_engine_for(lm, path)` helper. The existing `ExpertLM.chat`/`UnifiedLM.chat` single-sample methods stay as-is (raw quick path; no longer used by the agent).

## Verification
- Re-run the side-by-side probe (`expert` vs `specialist` on the same 8 prompts) and confirm expert replies become relevant (e.g. "do you like cats or dogs" → a cats/dogs answer, not a non-sequitur).
- Smoke-test `python -m sodachat.agent` loads in expert mode and replies; confirm `/model`, `/play`, `/score` still work (untouched paths).
- Confirm frontends (cli/discord/google) still construct `ChatEngine(backend=…)` and reply unchanged.

## Tradeoff (worth flagging)
MMI does ~12 candidate generations + ~24 logprob passes per reply instead of 1. The specialist/mini path already pays this (it's the documented relevance cost). The expert model is ~192MB vs mini's ~55MB, so expert replies on CPU will get slower (rough estimate: ~1-2s/reply). This is the explicit relevance/latency tradeoff the README describes, and the user's complaint is irrelevance — so MMI-on is the right default. If latency becomes objectionable, `_NUM_CANDIDATES` can be tuned per-backend later; not part of this change.
